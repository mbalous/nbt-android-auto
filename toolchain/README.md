# Open QNX 6.5.0 x86 toolchain (no SDP, no licence, no VM)

Builds the head-unit programs with GCC 4.4.2, the compiler version of QNX SDP 6.5.0, without the QNX SDP. Everything
comes from open sources or was written for this project:

| Part | Where it comes from |
|---|---|
| binutils 2.20.1, GCC 4.4.2 (C, C++), libgcc, libstdc++ | Official GNU releases (SHA-256 pinned in `setup.sh`). GCC already supports `i486-pc-nto-qnx6.5.0`. One small patch: [`patches/gcc-4.4.2-nto-pragma-pack.patch`](patches/) (`#pragma pack(push,n)`, as in QNX's GCC). |
| C headers ([`sysroot/usr/include`](sysroot/usr/include)) | Written for this project from the public QNX 6.5.0 library and USB DDK reference. Only what this project uses. |
| `crt1.o`, `crti.o`, `crtn.o` ([`runtime/`](runtime/)) | Written for this project. Same start-up sequence as SDP-built binaries. |
| `libc.so.3`, `libm.so.2`, `libsocket.so.3`, `libusbdi.so.2` | **Link-only stubs** generated by [`runtime/mkstub.py`](runtime/mkstub.py): just symbol names. They are never shipped. On the NBT, the real libraries are loaded. |
| `popen`/`pclose` ([`runtime/popen.c`](runtime/popen.c)) | Written for this project. QNX only has them in the static libc. |

## Setup (once, about 15–30 minutes)

Needs Docker on Linux or WSL and `sha256sum` for archive verification.

```sh
toolchain/setup.sh
```

Result: `build/qnx-open` (about 80 MB, git-ignored). Run any tool with `toolchain/qnx-open`, for example
`toolchain/qnx-open i486-pc-nto-qnx6.5.0-gcc -v`.

## Build the programs

```sh
python3 scripts/build_open.py
python3 installer/make_payload.py <version> --built build/open-build-<time>-<id> --pem-dir <payload>/rt
```

`build_open.py` prepares the sources exactly like `build_all.py` (NBT-AAD at cd1d9f8, overlay, patches, Mbed TLS
3.6.7). It then runs [`scripts/build-open.sh`](../scripts/build-open.sh). The open build uses link-only HMI stubs for
the plugin by default; `--hmi-libs` selects real BMW frameworks. The default open build also includes
`accessory_window` and the `nbt_key` and `nbt_a2i_beep` test tools. Resource-manager declarations are a limited,
experimental subset. The beep diagnostic is not included in the installer payload and loads the car's
`liba2i_client.so` at runtime.

[`../flash-aa-open.sh`](../flash-aa-open.sh) builds only by default; `--install` or `--install-only` explicitly
requests an **unsupported experimental** installation. Supported vehicle deployments must use binaries built in the
QNX 6.5.0 VM (`scripts/build_all.py`). Link-only stubs and hand-written headers do not establish ABI compatibility or
vehicle safety.

See [COMPARISON.md](COMPARISON.md) for a same-source open-versus-SDP build comparison and the remaining validation
needed before considering the open toolchain for releases.

## How it differs from an SDP build

- The C++ programs link GNU libstdc++ **statically** instead of Dinkum `libcpp.so.4`, so they are bigger (about
  210–260 KB instead of 50–100 KB). They need only `libc.so.3` and `libm.so.2` on the car.
- Upstream compared the earlier release sources (commit 1a12f0e) function by function with the 2026.11.10.2
  release binaries; this does not establish equivalence for the merged code:
  - Upstream compared its then-current service and USB code, apart from addresses.
  - Struct offsets, USB DDK constants, `PTHREAD_MUTEX_INITIALIZER`, `st_mtime`, `RLIMIT_CORE` and the socket
    symbol versions match.
- Every imported symbol is either imported by an SDP-built binary already, or is a standard POSIX/C function of
  libc.so.3 or libm.so.2.

## Limits

- Not run on the car yet. Test on the NBT before releasing.
- The headers cover what this project uses. A new system API (PPS, Screen, ...) needs its
  declarations added in `sysroot/` and its symbols added to the stubs. Check new struct layouts against an
  SDP-built binary first.

The default open build checks that every selected output is present and nonempty. `--programs` selects a
space-separated subset; unknown names fail rather than producing a misleading success. Use
`--output-dir build/<new-directory>` for a predictable output location; otherwise a unique directory is created.
`--reuse` can supply compatible binaries omitted by a selective build, but never overrides a built output.

CI checks the built binaries' ELF class and architecture and retains the experimental programs, resources, build log,
SHA-256 hashes and `readelf` metadata as a workflow artifact for 14 days. The report supports comparison with an SDP
build; it does not prove ABI compatibility or make the artifacts safe for vehicle deployment.

## ABI comparison and VM probes

The open and SDP builders write `abi-inputs.json` with the prepared source digest, revision and dirty status, pinned
inputs, compiler/linker information, HMI link mode, and binary hashes and origins. The open build also hashes its
installed compiler and sysroot. A matching source digest is not proof of equivalent flags, libraries or runtimes.

From the same clean revision, make fresh builds without `--reuse`; use the paths printed by the builders:

```sh
python3 scripts/build_open.py
python3 scripts/build_all.py --hmi-libs '$HOME/.nbt-build/hmi-libs'
python3 scripts/compare_qnx_abi.py --open build/open-build-<id> --sdp build/qnx-build-<id> \
  --output build/abi-comparison.json
```

An optional `--reference <local-payload-or-backup>` includes an older local binary reference, for observation only.
Keep private reference binaries and reports local. The JSON inventories dynamic symbols, versions, loader,
dependencies, search paths and relocations; missing and reused outputs are explicit. Dirty or mismatched provenance
is observational. Differences are advisory, but malformed ELF files and extraction or hash errors fail. CI uploads
an open-only inventory and does not need SDP or vehicle inputs.

With the documented, trusted host-only QNX VM reachable over SSH, the following builds and runs a separate probe with
both compilers under the non-root VM user. Replace the address with the verified VM address:

```sh
python3 scripts/test_open_abi_vm.py --vm-address 192.168.56.101
```

On Fedora, a VM whose SSH server only offers `ssh-rsa` may require prefixing this command and `build_all.py` with
`OPENSSL_ENABLE_SHA1_SIGNATURES=1`. Apply it only to the command using the trusted, host-key-pinned VM; do not weaken
the system-wide crypto policy.

Evidence in `build/open-abi-probe-*` covers constructor/destructor execution, libc and thread-local `errno`, selected
USB and resource-manager layouts and constants, local-only resource-manager setup and dispatch timeouts, iovec bytes,
and `devctlv` lookup and its invalid-descriptor error path. Local-only attachment registers no pathname and does not
exercise the accessory-window path-denial or cleanup self-test. The probes do not load the plugin, exercise USB
hardware, start a vehicle service, or establish behavior on the car. VM files are retained on failure. The HMI, C++
runtime and resource-manager behavior boundaries still need validation.

For the separate path-denial self-test, run the SDP-built and open-built `accessory_window` binaries **without
arguments** as root on an isolated QNX VM. Each creates its own temporary files and checks expiry, SIGTERM and SIGKILL
cleanup; a failure may leave its test directory under `/tmp`. Do not use the vehicle-window options for this test.
Both builds passed this self-test on the available VM; this does not establish vehicle compatibility.

## HMI link-only stubs

### Build matrix

| Compiler | BMW frameworks | Command | Status |
|---|---|---|---|
| QNX SDP VM | Real | `python3 scripts/build_all.py --hmi-libs '$HOME/.nbt-build/hmi-libs'` | Supported SDP build path; requires the real libraries in the VM. |
| QNX SDP VM | Stubs | `python3 scripts/build_all.py --hmi-stubs` | Experimental; installer opt-in required. |
| Open toolchain | Real | `python3 scripts/build_open.py --hmi-libs /path/to/hmi-libs` | Experimental; libraries are local to the host. |
| Open toolchain | Stubs | `python3 scripts/build_open.py --hmi-stubs` | Experimental; also the default open mode. |

Each real-framework directory must contain `libAppFramework.A.so` and `libCoreFramework.A.so` from your own NBT.
The VM builder defaults to real libraries at `~/.nbt-build/hmi-libs` and skips the plugin if they are missing;
an explicit `--hmi-libs` fails instead. The open builder mounts the selected local directory read-only and does not
copy its libraries into the source archive or payload. Never publish proprietary libraries. The open builder still
uses a link-only `libcpp-ne.so.4` stub in **both** modes; the VM builder uses the SDP C++ runtime.

A `--programs` selection that excludes the plugin does not exercise any HMI link mode; its provenance reports
`missing` or `reused`.
All open builds and SDP stub builds remain unqualified for vehicle deployment, regardless of linking success.
CI exercises the open real-framework code path with synthetic fixtures, not proprietary BMW libraries.
Provenance records the selected mode; it does not authenticate the supplied libraries.

Both the open build and the opt-in SDP stub build generate C sources from `toolchain/hmi-stubs/contract.json` on
the host before preparing the source archive. These provide symbol names for the BMW framework and the open build's
C++ link, but are never runtime libraries and must not be installed. CI checks the generated stub SONAMEs and exports,
the open plugin's dependencies, imports and exports against the contract, and excludes stub files from build artifacts.
The packaging test also checks that a stub in the build output is not included in the payload. CI removes one stub
symbol in an isolated fixture and confirms that the plugin link fails.

Review intentional changes to the symbol contract against the target and update the contract explicitly; do not
regenerate it blindly from the build. Successful checks establish link-time consistency only, not C++ ABI or real HMI
behavior. SDP and vehicle qualification remain separate.
